# v3-update-1 — оркестрованный ассистент

Актуальная версия флоу в Langflow. Собрана поверх v3, но с другой схемой
управления: логику интервью ведёт код, а модель отвечает только за язык.

Предыдущие версии не тронуты и лежат рядом: `Interview Bot (agentic)` — первая
агентная, `Interview Bot (v3 — orchestrated)` — исходная третья.

---

## Архитектура

**7 узлов, 7 рёбер.**

```
Chat Input ─┬─────────────────────────────────────────► Agent (input_value)
            │
            └──► Interview Controller ──► Agent (system_prompt)
                        ▲
                  gpt-oss-120b (оценка)

Yandex Chat Model ─────────────────────► Agent (model)
Verdict R1-R5 (tool) ──────────────────► Agent (tools)
Yandex Web Search (tool) ──────────────► Agent (tools)

Agent ─────────────────────────────────► Chat Output
```

### Ключевое отличие от v3

В v3 контроллер был **инструментом** `submit_answer`, который агент должен был
вызывать после каждого ответа. На практике он этого не делал: в замерах агент
вызвал инструмент **1 раз из 5**, а остальные ходы вёл разговор сам, без оценок
и без учёта бюджета вопросов.

Теперь контроллер — **обычный узел графа**. Langflow исполняет его на каждом ходу
принудительно, потому что он стоит между Chat Input и системным промптом агента.
Пропустить его невозможно: инструмента `submit_answer` больше не существует.

Результат: **5 вызовов из 5** в каждом прогоне.

### Кто за что отвечает

| Узел | Роль | Кто решает |
|---|---|---|
| **Interview Controller** | Читает разговор, ставит оценки 0/1/2, ведёт счётчики попыток и бюджет, выбирает следующую тему, собирает системный промпт | Код |
| **Agent** | Формулирует вопрос по назначенной теме, в конце пересказывает вердикт | Модель |
| **Verdict R1-R5** | Правила R1–R5, считает вердикт по оценкам из состояния | Код |
| **Yandex Web Search** | Ищет работающие аналоги, возвращает реальные ссылки | Инструмент AI Studio |
| **Yandex Chat Model** | Модель для агента | — |

Агент не выбирает тему, не считает попытки и не выносит вердикт. Он не может
проскочить тему, потому что тема приходит ему в системном промпте уже готовой.

## Модели

| Где | Поле | Модель | Почему |
|---|---|---|---|
| Yandex Chat Model | `Model` | `deepseek-v4-flash/latest` | Формулировки читает человек. В сравнении семи моделей единственный, кто соблюдал правило двух попыток и не подсказывал признаки аудитории |
| Interview Controller | `Scoring Model` | `gpt-oss-120b` | Служебная оценка в JSON, человек её не видит. Втрое быстрее deepseek при том же объёме вывода |
| Yandex Web Search | `Model` | `yandexgpt/latest` | Работает, не трогали |

### Замеры на промпте оценки

| Модель | Время | Токенов на выходе |
|---|---|---|
| **gpt-oss-120b** | **6,9 с** | 674 |
| deepseek-v4-flash | 19,6 с | 732 |
| qwen3.6-35b-a3b | 14,4 с | 2245 |

`qwen3.6` пробовали — **откатили**. В изоляции он быстрый, но внутри флоу ход
зависал дольше двух минут. Скорее всего из-за втрое большего объёма вывода: вызов
не укладывался в таймаут 90 с и уходил на повтор. Точную причину не ловили —
откатили сразу, чтобы вернуть рабочую систему.

`gpt-oss-120b` на первом ходу склонен ставить сегменту 1 там, где deepseek ставил
0, то есть чуть щедрее на старте. На итоговый вердикт в прогонах не повлияло.
Если вердикты покажутся мягкими — вернуть deepseek правкой одного поля.

## Производительность

| | Было (v3) | Стало |
|---|---|---|
| Ход с вопросом | 15–38 с | **11–18 с** |
| Финальный ход с поиском | 48–69 с | **26 с** |
| Вызовов контроллера | 1 из 5 | **5 из 5** |

Каждый ход — два последовательных обращения к модели: оценка (gpt-oss) и
формулировка вопроса (deepseek). Это структурная цена оркестрации.

### Что дало ускорение

1. **Лимит «вопрос не длиннее 25 слов»** — главный выигрыш. На чистом замере
   deepseek: 24,4 с и 1019 токенов без лимита против **2,0 с и 60 токенов** с
   лимитом. Модель по умолчанию писала простыню там, где нужен один вопрос.
   Лимит намеренно **не действует** на финальный пересказ вердикта — там нужны
   вердикт, заметка о рынке и четыре пункта домашки.
2. **Убрано поле `evidence`** из схемы оценки. Оно писалось в состояние, но нигде
   не использовалось — в инструкцию агенту шло только `missing`.
3. **`missing` ограничен 10 словами.**
4. **Оценка только открытых тем.** Схема строится динамически; когда все темы
   закрыты, вызов не делается вообще.
5. **Расшифровка обрезана до 10 последних реплик.** Оценки монотонные, поэтому
   уже закрытое хранится в состоянии и перечитывать историю целиком не нужно.

Проверенная гипотеза, оказавшаяся **неверной**: строгая JSON-схема не виновата.
Обычный текст на deepseek занимал те же 17,5 с, что и `strict=True` — 16,8 с.
Дело было в объёме вывода, а не в режиме генерации. Поле `reasoning_tokens` во
всех замерах равно 0, то есть «думающая модель» тоже не подтвердилась.

## Исправленные ошибки

### 1. Память падала внутри инструмента

Обращения к памяти Langflow рушились с

```
StatementError: 'str' object has no attribute 'hex'
```

Внутри вызова инструмента `self.graph` подменяется на `PlaceholderGraph`, у
которого `flow_id` — строка, а SQLAlchemy ждёт UUID. Голый `except Exception`
это молча съедал.

Последствия были тяжёлыми и невидимыми: расшифровка получалась длиной 48
символов (только последняя реплика), а состояние не загружалось **никогда**. То
есть контроллер оценивал одну фразу в вакууме и каждый ход начинал с нуля.
Отсюда «ты уже спрашивал об этом» и хаотичный порядок тем.

Исправлено методом `_flow_uuid()`: приводит `flow_id` к UUID, при неудаче
возвращает `None` — `session_id` и так однозначно ограничивает выборку.

### 2. Типы аргументов вердикта

Агент передавал `not_tech` булевым в строковое поле, Langflow отбраковывал
вызов и агент повторял его — лишний прогон на 26 780 токенов и 69 секунд.

Теперь у `compute_verdict` **один** аргумент — `market_count`. Оценки, `entry`
и `not_tech` Verdict читает из состояния сам. Подставлять нечего, ломаться нечему.

### 3. Оценка в вакууме

v3 оценивал один ответ без контекста, хотя в промпте оценщика было написано
«засчитывай сказанное в ЛЮБОМ месте разговора» — требование невыполнимое.
Теперь оценщик читает расшифровку и ставит баллы по всем открытым темам сразу,
монотонным слиянием, как в исходном `core/interview.py:_read_state()`.

### 4. Резервный системный промпт

Статичное поле `system_prompt` у агента перекрывается связью от контроллера. Там
лежит полноценная персона с правилами и дефолтным вопросом про аудиторию, а не
заглушка с ошибкой: если связь оборвётся, ассистент продолжит вести интервью
корректно, просто без адаптивного выбора темы.

### 5. Фронтенд стирал связи контроллера

При открытии флоу Langflow показывал предупреждение «Some connections were removed
because they were invalid» и удалял оба ребра контроллера. Причина — в описании
связи я указал `"type": "other"`, тогда как для строковых полей фронтенд ждёт
`"type": "str"` и всё остальное отбраковывает. Связи пересобраны так, что тип
берётся из описания самого поля, а не задаётся вручную.

Первоначальный диагноз («вкладка перезаписывает базу своей копией») был **неверным**
— перезаписи не было, фронтенд именно валидировал и удалял.

### 6. Ложный вердикт при потере состояния

Самый тяжёлый дефект: ассистент выдал уверенный, подробно аргументированный и
полностью **неверный** вердикт. Все четыре темы были закрыты на 2, а участнику
сказали «доработать» и выдали домашнее задание по всем темам.

Механизм: в графе оказалась старая версия компонента вердикта, без `_flow_uuid()`
и с пятью аргументами. Чтение состояния падало, голый `except` возвращал `None`,
дальше подставлялись нули — и по нулям срабатывало правило R2. Из чата это было
неотличимо от нормальной работы.

Исправлено дважды. Компонент заменён на правильную версию. И вдобавок расчёт
вердикта теперь **падает громко**: вместо подстановки нулей выбрасывается ошибка с
понятным текстом, а в само сообщение об ошибке вшита инструкция агенту — не
выносить вердикт самому и сказать человеку про технический сбой.

Проверено на живом прогоне: при сломанном чтении состояния ассистент отвечает
«технический сбой — вердикт посчитать не удалось» и решение не выдумывает.

Ошибок в компоненте вердикта больше не глушится: `raise ValueError` — четыре
штуки, `return {}` — ни одного. Ошибка оценки в контроллере остаётся не
фатальной (интервью не должно обрываться), но пишется в `status` узла и в
состояние как `last_score_error`.

## Что осталось незакрытым

- **Согласованность оценок не измерена.** Размеченного датасета нет, поэтому
  неизвестно, насколько устойчиво модель ставит одни и те же баллы на одной и
  той же расшифровке. Это условие промышленного использования.
- **Причина зависания на qwen не доказана**, только правдоподобная гипотеза.
