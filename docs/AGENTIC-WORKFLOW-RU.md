# Агентный воркфлоу «Первый фильтр акселератора» в Langflow

Дата: 2026-08-04. Флоу: **Interview Bot (agentic)**, id `45fd9442-d8a7-4cb4-97c4-3922e153e015`,
проект Starter Project, локальный Langflow на `http://localhost:7860`.

Исходный ручной флоу на 16 узлов сохранён нетронутым под именем **New Flow (1)** —
на него ничего из описанного ниже не влияет.

---

## 1. Зачем переписывали

Первая версия была перенесена из питоновского `ai-accel/core/*.py` «один в один»:
каждая функция стала отдельным кастомным узлом. Получилось 16 узлов, из которых
около десяти — чистая обвязка, существовавшая только чтобы перекладывать состояние
между шагами: `Load State`, `Save State`, `Merge State`, `Transcript Builder`,
`State Prompt Builder`, `Build Focus Prompt`, `Topic Router`, `Record Attempt`,
`Build Search Query`.

Проблемы этого подхода:

- Полотно нечитаемо, связи путаются, добавить новый агентный узел практически
  невозможно — непонятно, куда его втыкать.
- Каждая мелкая правка требовала ручного перетаскивания рёбер.
- Половина узлов не несла продуктовой ценности, а только «чинила» поток.

Ключевое наблюдение: у компонента `Agent` в Langflow **память диалога уже есть**
(параметр `n_messages`). Значит вся обвязка вокруг состояния не нужна в принципе.

## 2. Что получилось

**6 узлов вместо 16, 5 рёбер:**

```
Chat Input ──────────────► Agent ──► Chat Output
Yandex Chat Model ───────►  │  (model)
Verdict R1-R5 (tool) ────►  │  (tools)
Yandex Web Search (tool) ─►  │  (tools)
```

| Узел | Тип | Роль |
|---|---|---|
| `Chat Input` | нативный | вход из Playground |
| `Yandex Chat Model` | кастомный | отдаёт `ChatOpenAI` на OpenAI-совместимый эндпоинт Яндекса, типизирован как `LanguageModel` |
| `Agent` | нативный | весь интервьюер: персона, четыре темы, рубрика, запреты, бюджет вопросов; память через `n_messages=100` |
| `Verdict R1-R5` | кастомный, Tool Mode | детерминированные правила R1–R5, инструмент `compute_verdict` |
| `Yandex Web Search` | кастомный, Tool Mode | проверка рынка, инструмент `search_market` |
| `Chat Output` | нативный | выход в Playground |

Модель: **`deepseek-v4-flash/latest`** (см. раздел 5 — это не косметический выбор).

### Что осознанно осталось кодом

`Verdict R1-R5` остаётся детерминированным и вызывается как инструмент. Причина:
правила R1–R5 — это и есть решение о прохождении, оно должно быть воспроизводимым
и проверяемым по логу. Оценки по темам приносит модель, но арифметику правил
считает код.

### Что осознанно выброшено

`Reply Filter` не переносился. Его работа (один вопрос, без выдуманных реплик, без
плейсхолдеров) теперь описана в инструкциях агента. Если бы он остался, он бы
портил финальное сообщение с вердиктом — он обрезает текст после первого «?».

Проблема «запускать поиск рынка только на стадии market» исчезла сама: агент
вызывает инструмент тогда, когда интервью закончилось. Отдельный гейт не нужен.

## 3. Находки по ходу работы

### 3.1 Yandex умеет function calling
Проверено напрямую, до того как строить дизайн: и «сырой» вызов
`chat.completions.create(tools=[...])`, и `ChatOpenAI.bind_tools()` через LangChain
возвращают корректные `tool_calls`. Без этого агентная схема была бы невозможна.
Базовый URL: `https://ai.api.cloud.yandex.net/v1`.

Оговорка: `yandexgpt/latest` вернул `tool_calls` в изолированном тесте, но не
вернул в прогоне бенчмарка — поддержка нестабильная. Ещё один довод уйти с него.

### 3.2 Langflow вырезает секреты при создании флоу через API
Флоу, созданный через `POST /api/v1/flows/`, теряет значения полей
`SecretStrInput`. Всё остальное (`folder_id`, `system_prompt`, `n_messages`)
сохраняется штатно. API-ключ приходится вводить руками в UI. Поведение разумное с
точки зрения безопасности, но о нём надо знать.

### 3.3 `targetHandle.type` обязан совпадать с типом поля
Иначе фронтенд **молча удаляет ребро** при ближайшем автосохранении. Ни ошибки, ни
уведомления — флоу просто перестаёт работать.

| Поле | Правильный `type` |
|---|---|
| `input_value` у Agent | `str` |
| `model` у Agent | `model` |
| `tools` у Agent | `other` |

Именно на этом потерялись два ребра при первом создании флоу, и то же самое
раньше съело ребро при импорте JSON.

### 3.4 UI перезаписывает правки, сделанные через API
Если вкладка с флоу открыта, фронтенд держит свою копию в памяти и при
автосохранении затирает всё, что изменено через API. Один тест из-за этого дал
ложный результат: правка промпта откатилась, а прогон шёл по старой версии.

**Правило: перед PATCH через API уйти со страницы флоу, применить правку,
проверить в БД, только потом открывать флоу заново.**

### 3.5 Баг с `session_id`
Компоненты падали с `AttributeError: Attribute session_id not found`.
Причина: Langflow заполняет атрибут `self.session_id` только если в шаблоне
компонента есть поле, буквально названное `session_id`
(`lfx/graph/vertex/base.py`: `self.has_session_id = "session_id" in template_dicts`).
У нас поле называлось `session_id_override`, поэтому `self.session_id` не
существовал. Пока в поле-переопределении лежало тестовое значение, выражение
`self.session_id_override or self.session_id` до падения не доходило — баг
проявлялся только при пустом поле, то есть в бою.

Лечение: `self.graph.session_id` вместо `self.session_id`.

### 3.6 Правило «две попытки на тему» промптом не держится
Главная находка. На заведомо слабом ответе («строительные компании и их
поставщики» — это целая категория, по рубрике единица) агент засчитывал тему и шёл
дальше. Интервью укладывалось в 4 вопроса вместо 6–8, а вердикт потом ругал
человека ровно за ту размытость, которую сам не стал докапывать.

Две правки промпта подряд **не помогли** (проверено, что новый промпт реально лежал
в БД во время прогона):

1. «На одну тему максимум 2 вопроса» — читается как потолок, одного вопроса
   достаточно, чтобы его не нарушить.
2. Явный блок «ПРАВИЛО ДВУХ ПОПЫТОК» с пошаговым разбором счёта и примерами
   ответов, которые никогда не тянут на 2 — всё равно пропускал второй вопрос.

Вывод: счётные правила и правила о состоянии («сколько вопросов я уже задал по этой
теме») — ровно то, в чём LLM ненадёжна и что в исходном питоне держалось кодом
(`session.attempts[dim] += 1` плюс `_current_dim()`).

### 3.7 Дело оказалось в модели, а не в промпте
Прогнали все чат-модели, доступные аккаунту, на том самом провальном ходу
(системный промпт + «строительные компании и их поставщики» → задаст второй вопрос
по Аудитории или перескочит на Поведение?) и заодно на поддержку инструментов:

| модель | инструменты | осталась на теме | соблюдение запретов |
|---|---|---|---|
| `yandexgpt/latest` (была) | нет | **нет** — перескочила | — |
| `yandexgpt-5.1` | да | да | нарушает 5а («по масштабу проектов») |
| `yandexgpt-5-pro` | **нет** | да | непригодна: без tool calling |
| **`deepseek-v4-flash`** | да | да | чисто — спрашивает про источник знания ровно по 5а |
| `qwen3-235b-a22b-fp8` | да | да | лёгкое нарушение 5а («в каком регионе») |
| `qwen3.6-35b-a3b` | да | да | чисто |
| `gpt-oss-120b` | да | да | нарушает 2 и 3 — выдаёт список примеров |

Переключили на `deepseek-v4-flash`. На том же слабом ответе он теперь отвечает
«Откуда ты про это знаешь — сам работал в стройке или уже общался с кем-то из этих
компаний?» — второй заход по той же теме, без подсказанного признака и без списка
вариантов.

Запасной вариант: `qwen3.6-35b-a3b`. Не использовать `yandexgpt-5-pro` (нет
инструментов) и `gpt-oss-120b` (подсказывает человеку готовые ответы).

### 3.8 Дрейф «перечисление вариантов в вопросе»
У deepseek осталась более мягкая версия той же проблемы: на теме Альтернативы он
спрашивал «Может, какие-то программы, каталоги, другие сервисы?» — то есть
перечислял варианты внутри вопроса, нарушая запреты 2 и 3.

Добавили в промпт пункты 2а и 2б с явным запретом перечислять категории решений
внутри вопроса и с требованием обрывать реплику после самого вопроса.
После правки: **3 прогона из 4 чистые**, в одном осталось родовое «какие способы,
сервисы или костыли» — мягче, чем было, но не идеально.

## 4. Полный прогон (проверено)

Интервью на 6 ходов, идея «ИИ-платформа для подбора бетонных плит»:

| Ход | Тема | Итог |
|---|---|---|
| 1–2 | Аудитория | слабый ответ → **второй заход** → закрыта («прораб в панельном домостроении, закупщики на двух ЖБИ») |
| 3 | Поведение | закрыта (18 000 ₽, два рейса, два раза в месяц) |
| 4 | Альтернативы | закрыта (Excel + 1С + замерщик за 5 000) |
| 5 | Проверка | закрыта (неделя, пять человек, критерий провала) |

Затем сработали **оба** инструмента — проверено в `content_blocks` сообщения, не на
глаз:

- `search_market` → реальные ссылки из веба (calculator.fixplans.ru и др.), 5 аналогов
- `compute_verdict` → `{"outcome": "pass", "rule": "R5", ...}`

Агент пересказал объяснение R5 и домашнее задание дословно из ответа компонента, а
не выдумал их. Разделение «модель говорит — код решает» держится.

## 5. Компромиссы

### Что выиграли
- 16 узлов → 6. Полотно читаемо, есть куда добавлять новые агентные узлы.
- Память диалога бесплатно, без узлов состояния и без скрытых `__state__` сообщений.
- Гейтинг рынка решился сам собой.
- Меньше мест, где всё молча ломается (рёбра, типы хендлов, порядок узлов).

### Чем заплатили
- **Оценки по темам ставит модель**, а не отдельный вызов READER со строгой
  JSON-схемой. Это бьёт по воспроизводимости и по плану с golden dataset и
  автоматическими эвалами: одну и ту же расшифровку модель может оценить по-разному.
- **Правила держатся моделью, а не кодом.** Сейчас правило двух попыток соблюдается
  потому, что модель достаточно сильная, а не потому, что что-то его гарантирует.
  Дрейф может вернуться на другой модели или после правки промпта.
- **Завязка на конкретную модель.** Работоспособность схемы проверена на
  `deepseek-v4-flash`; на `yandexgpt` она деградирует до неприемлемого.
- Версионирование промптов (`PROMPTS_VERSION` в исходном коде) в этой схеме пока
  никак не отражено.

### Как вернуть гарантии, если понадобится
Вынести контроллер обратно в код, но как **инструмент**: один узел с функцией вида
`next_step(topic, score)`, который владеет счётчиком попыток и возвращает агенту
прямую инструкцию («задай второй вопрос по Аудитории» / «переходи к Поведению»).
Счёт снова становится детерминированным, узел добавляется всего один. Остаётся
зависимость от того, что агент вызовет инструмент, но по опыту этой работы вызов
инструментов у моделей надёжнее, чем счёт в уме.

## 6. Что дальше

1. Решить принципиально: оставляем оценку на модели (быстро, читаемо) или
   возвращаем отдельный READER со строгой схемой (воспроизводимо, пригодно для
   эвалов). От этого зависит судьба задачи про golden dataset.
2. Если остаёмся на агенте — добить дрейф с перечислением вариантов до нуля.
3. Прогнать 5–10 разных идей и посмотреть на разброс вердиктов на одинаковых входах.
4. Вернуть учёт версии промпта в лог, иначе накопленные разговоры нельзя
   использовать для калибровки рубрик.
